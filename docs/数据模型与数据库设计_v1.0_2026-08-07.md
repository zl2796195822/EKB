# EKB 数据模型与数据库设计

> **配套文档**：[技术架构与详细设计](./技术架构与详细设计_v1.0_2026-08-07.md) · [API 接口契约](./API接口契约_v1.0_2026-08-07.md)  
> **文档版本**：v1.0（待评审）  
> **编写日期**：2026-08-07  
> **数据库基线**：PostgreSQL + pgvector（MVP 建议，M0 固定版本）

---

## 1. 设计原则

1. 所有租户内业务数据必须带 `tenant_id`，所有查询必须从服务端授权上下文注入租户条件。
2. 业务真相保存在 PostgreSQL；RAG 引擎和向量索引只保存派生数据，必须能从业务库重建。
3. 删除默认软删除；审计记录不可静默修改或删除，清理必须按留存策略执行。
4. 文档、chunk、消息和引用都要绑定版本，避免知识更新后历史回答不可复核。
5. 表结构优先保证安全和可追踪，再做性能优化；跨租户共享缓存和索引必须有显式隔离字段。

## 2. 枚举

实现前需要启用数据库扩展：

```sql
CREATE EXTENSION IF NOT EXISTS citext;
CREATE EXTENSION IF NOT EXISTS vector;
```

Embedding 维度在 M0 固定后再写入迁移脚本；设计稿阶段用 `EMBEDDING_DIM` 作为占位常量即可。

```sql
CREATE TYPE tenant_status AS ENUM ('ACTIVE', 'SUSPENDED', 'DELETED');
CREATE TYPE member_status AS ENUM ('ACTIVE', 'INVITED', 'DISABLED');
CREATE TYPE tenant_role AS ENUM ('OWNER', 'ADMIN', 'MEMBER', 'CUSTOMER');
CREATE TYPE platform_role AS ENUM ('NONE', 'SUPPORT', 'ADMIN');
CREATE TYPE kb_visibility AS ENUM ('PRIVATE', 'TEAM', 'PUBLIC');
CREATE TYPE kb_role AS ENUM ('OWNER', 'ADMIN', 'EDITOR', 'VIEWER');
CREATE TYPE document_status AS ENUM ('PROCESSING', 'READY', 'FAILED', 'DELETED');
CREATE TYPE source_type AS ENUM ('UPLOAD', 'URL', 'SYNC');
CREATE TYPE ingest_status AS ENUM ('QUEUED', 'RUNNING', 'SUCCEEDED', 'FAILED', 'CANCELLED');
CREATE TYPE message_role AS ENUM ('USER', 'ASSISTANT', 'SYSTEM');
CREATE TYPE feedback_rating AS ENUM ('UP', 'DOWN');
```

## 3. 核心表

> SQL 为逻辑设计稿，正式迁移脚本需在 M1 按实际 ORM/迁移工具生成并评审。

```sql
CREATE TABLE users (
  id UUID PRIMARY KEY,
  name TEXT NOT NULL,
  email CITEXT NOT NULL UNIQUE,
  password_hash TEXT,
  status member_status NOT NULL DEFAULT 'ACTIVE',
  created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
  updated_at TIMESTAMPTZ NOT NULL DEFAULT now(),
  deleted_at TIMESTAMPTZ
);

CREATE TABLE tenants (
  id UUID PRIMARY KEY,
  slug TEXT NOT NULL UNIQUE,
  name TEXT NOT NULL,
  status tenant_status NOT NULL DEFAULT 'ACTIVE',
  policy_version INTEGER NOT NULL DEFAULT 1,
  created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
  updated_at TIMESTAMPTZ NOT NULL DEFAULT now(),
  deleted_at TIMESTAMPTZ
);

CREATE TABLE tenant_memberships (
  id UUID PRIMARY KEY,
  tenant_id UUID NOT NULL REFERENCES tenants(id),
  user_id UUID NOT NULL REFERENCES users(id),
  role tenant_role NOT NULL,
  status member_status NOT NULL DEFAULT 'ACTIVE',
  created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
  updated_at TIMESTAMPTZ NOT NULL DEFAULT now(),
  UNIQUE (tenant_id, user_id)
);

CREATE TABLE platform_memberships (
  id UUID PRIMARY KEY,
  user_id UUID NOT NULL REFERENCES users(id),
  role platform_role NOT NULL DEFAULT 'NONE',
  status member_status NOT NULL DEFAULT 'ACTIVE',
  created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
  UNIQUE (user_id)
);
```

```sql
CREATE TABLE teams (
  id UUID PRIMARY KEY,

CREATE TABLE team_members (

CREATE TABLE knowledge_bases (

  tenant_id UUID NOT NULL REFERENCES tenants(id),

  owner_id UUID NOT NULL REFERENCES users(id),

CREATE TABLE kb_acl_entries (
```

## 4. 索引建议

```sql
CREATE INDEX idx_memberships_tenant_user ON tenant_memberships (tenant_id, user_id) WHERE status = 'ACTIVE';
CREATE INDEX idx_kb_tenant_visibility ON knowledge_bases (tenant_id, visibility) WHERE deleted_at IS NULL;
CREATE INDEX idx_kb_acl_subject ON kb_acl_entries (tenant_id, subject_type, subject_id, kb_id);
CREATE INDEX idx_docs_tenant_kb_status ON documents (tenant_id, kb_id, status) WHERE deleted_at IS NULL;
CREATE INDEX idx_jobs_tenant_status ON ingest_jobs (tenant_id, status, updated_at);
CREATE INDEX idx_chunks_tenant_kb_doc ON chunks (tenant_id, kb_id, doc_id, doc_version) WHERE deleted_at IS NULL;
CREATE INDEX idx_chunks_search_tsv ON chunks USING GIN (search_tsv);
CREATE INDEX idx_chunks_metadata ON chunks USING GIN (metadata);
CREATE INDEX idx_conversations_user ON conversations (tenant_id, user_id, updated_at DESC) WHERE deleted_at IS NULL;
CREATE INDEX idx_messages_conversation ON messages (tenant_id, conversation_id, created_at);
CREATE INDEX idx_citations_message ON message_citations (tenant_id, message_id, rank);
CREATE INDEX idx_audit_tenant_time ON audit_logs (tenant_id, created_at DESC);
CREATE INDEX idx_audit_trace ON audit_logs (trace_id);
```

向量索引类型、维度和参数必须在 M0 固定 Embedding 模型后确定。不同 Embedding 维度不得混写到同一索引。

## 5. 租户隔离策略

| 层 | 策略 |
|---|---|
| 应用 | 所有 repository/service 方法强制接收 `AuthContext` 或 `tenant_id`，不允许裸查询 |
| 数据库 | 表含 `tenant_id`；关键唯一索引包含 `tenant_id`；可在 M2 评估 PostgreSQL RLS |
| 向量 | chunk 元数据保存 `tenant_id,kb_id,doc_id,acl_fingerprint` |
| 对象存储 | object key 包含租户和文档版本，例如 `tenants/{tenant_id}/kb/{kb_id}/docs/{doc_id}/v{version}` |
| 缓存 | key 包含租户、主体权限摘要、知识版本和策略版本 |
| 审计 | 跨租户管理动作必须有平台角色和二次确认记录 |

## 6. 迁移与回滚规则

1. 每个迁移必须可在空库和已有测试数据上重复验证。
2. 扩字段先兼容读写，再切换使用，最后清理旧字段；避免同版本破坏性变更。
3. 枚举新增值前必须确认前端、API 和测试都能处理未知值或灰度发布。
4. 涉及大表回填时使用批处理任务，记录游标、重试和失败原因。
5. 回滚不删除审计记录；如需禁用功能，通过配置或 feature flag 降级。

## 7. 数据留存与清理

| 数据 | 默认策略 | M0/M1 待冻结 |
|---|---|---|
| 原始文档 | 随知识库保留，删除后软删除和延迟清理 | 延迟清理周期 |
| chunk 和索引 | 文档删除或版本下线后不可检索，可重建 | 索引重建策略 |
| 会话消息 | 按租户策略保留，敏感内容可加密保存 | 留存期限、脱敏规则 |
| 审计日志 | 不可静默修改，按合规期限保留 | 合规期限、导出审批 |
| 评估集 | 只用脱敏样本，版本化保存 | 标注权限、样本规模 |

## 8. DB 评审门禁

- [ ] 每个业务表都有主键、时间戳、租户边界或明确的平台级例外。
- [ ] 每个跨实体查询都有对应索引或容量解释。
- [ ] 软删除数据不会进入检索、引用、导出和对象签名。
- [ ] 向量维度、索引类型和模型版本在 M0/M1 明确。
- [ ] 审计和密钥相关表不保存明文敏感信息。

---

_数据库设计要服务于“可授权、可追溯、可重建”。MVP 可以简单，但不能把租户和版本边界留给以后补。_
