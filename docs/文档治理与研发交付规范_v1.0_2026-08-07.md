# EKB 文档治理与研发交付规范

> **文档类型**：Reference  
> **目标**：把需求、设计、代码、测试、发布、Skills 和 MCP 证据连接成一条可追溯链路。  
> **适用对象**：产品、前端、后端、AI/RAG、QA、安全、运维和文档维护者。  
> **文档版本**：v1.0（待评审）  
> **编写日期**：2026-08-07  

## 摘要

本文规定 EKB 文档的权威顺序、生命周期、变更影响、评审门禁和交付证据。任何影响需求、API、数据模型、安全边界、质量指标或部署方式的变更，都必须先判断影响范围，再同步相关文档，最后才进入实现或发布。

本文不替代产品需求、技术设计、安全评审、测试报告或正式验收。它只规定这些材料如何协同、如何留痕和如何退出。

## 1. 文档基线与权威顺序

项目资料按以下顺序生效：

1. 已批准的项目决策记录和安全边界
2. 企业级知识库 Spec 与 MVP 验收标准
3. API 契约、数据模型、技术架构和 UI 设计
4. RAG 评估、测试策略、部署运维和灾备手册
5. 项目任务分解与 Backlog
6. 本文档和 `Skills/<skill>/SKILL.md`

出现冲突时，执行更高优先级的规则，并在任务记录中写明偏差、原因、风险和批准人。Skill 只能提供方法与检查项，不能放宽权限、出域、审计、测试或发布门禁。

## 2. 文档生命周期

| 状态 | 进入条件 | 可执行范围 | 退出动作 |
|---|---|---|---|
| 草稿 | 有明确 Owner 和目标读者 | 仅用于评审准备 | 补齐依据、影响范围和开放问题 |
| 评审中 | 变更内容和关联文档已列出 | 可做 PoC，不得作为上线基线 | 完成评审意见和决策记录 |
| 已批准 | Owner、技术、安全或 QA 完成对应签署 | 可作为开发、测试或发布输入 | 发生边界变化时升级版本 |
| 已替代 | 新版本已批准 | 不得作为新任务依据 | 保留链接、替代版本和失效原因 |
| 已归档 | 项目范围移除或材料不再适用 | 只读 | 保留审计和追溯所需信息 |

每份文档至少保留标题、用途、版本、日期、Owner、状态、配套文档和开放问题。正式版本不覆盖历史版本，使用新版本号和日期替换。

## 4. 变更影响矩阵

先判断变更类型，再同步下表中的文档。只改代码、不改契约的做法不适用于跨边界变更。

| 变更类型 | 至少同步的文档 | 必须留下的证据 |
|---|---|---|
| 新增或删除功能 | Spec、MVP、Backlog、测试策略 | 需求编号、验收标准、风险和 Owner |
| 修改 API 路径、字段或错误码 | API、MVP、技术架构、测试策略 | 契约 diff、兼容性说明、回归用例 |
| 修改表、索引、租户或版本边界 | 数据模型、API、技术架构、安全、测试 | 迁移方案、回滚方案、越权测试 |
| 修改检索、切分、Prompt、模型或引用 | RAG 方案、技术架构、MVP、测试策略 | 评估集版本、对比结果和降级策略 |
| 修改认证、ACL、缓存或数据出域 | 安全、Spec、API、数据模型、部署运维 | 威胁路径、控制措施和安全批准 |
| 引入外部依赖、MCP 或基础设施 | 技术架构、部署运维、测试、决策记录、MCP 规范 | 版本、commit、许可证、访问范围、容量依据和替换成本 |
| 修改 UI 流程、状态或文案 | UI、MVP、测试策略、相关 API | 状态清单、响应式截图和可访问性证据 |
| 修改 AI 对话流协议、取消或回放 | 流式交互设计、API、MVP、DB、UI、测试、决策记录 | 事件契约、状态机、迁移/回滚、取消竞态、灰度和性能证据 |
| 修改发布、备份或恢复方式 | 部署运维、安全、测试、决策记录 | 演练记录、RPO/RTO、回滚步骤 |

## 5. 需求到交付的追踪链

每个可交付变更都必须能沿以下链路回溯：

```text
需求编号
  → MVP 验收编号
  → Backlog 任务 ID
  → API/DB/UI/安全设计
  → 测试用例或评估样本
  → Review 与发布证据
```

新增需求使用已有 `FR-*` 编号规则；验收使用 `AC-*`；任务使用 `M0-*` 至 `M5-*`。编号一旦进入已批准文档，不得复用。

无法自动化的验收项必须保存手工记录、截图、日志或评审结论，并关联任务 ID。只写“已验证”不算证据。

## 6. 任务开始前的开发门禁

实现者在开始编码前必须完成以下检查：

1. 确认任务 ID、需求编号、依赖、风险、验收标准、`Skill refs` 和 `MCP refs`
2. 读取 `Skills/<skill>/SKILL.md` 和 [MCP 工具与项目使用规范](./MCP工具与项目使用规范_v1.0_2026-08-07.md)，并按指引读取实际需要的规则文件
3. 检查 API、数据模型、安全边界和 UI 状态是否已有基线
4. 记录实现假设、敏感数据边界、MCP 访问范围和需要更新的文档
5. 确认测试环境使用脱敏数据，密钥、证书和真实地址不进入仓库

M0/M1 的阻塞开放问题没有批准的降级方案时，不得用代码中的隐式假设代替决策。

## 7. 任务完成时的交付证据

任务说明、合并请求或变更记录必须包含以下内容：

```text
Task ID: M1-xx
Requirement refs: FR-xx, AC-xx
Skill refs: security-best-practices, playwright
Read: Skills/<skill>/SKILL.md 和实际使用的规则文件
MCP refs: playwright-mcp / github-mcp-server / postgres-mcp / none
MCP snapshot: MCP/registry.json 中的 commit SHA、访问范围和批准记录
Applied: 采用的规则与对应代码/文档位置
Validation: 测试命令、评估结果、截图、trace 或评审结论
Docs updated: 本次同步的文档和版本
Exceptions: 未采用的规则、原因、风险和决策编号
```

交付证据必须能让没有参与实现的人复核。测试失败、暂缓项和已知限制不能隐藏在聊天记录里。

## 8. 里程碑评审门禁

| 阶段 | 必须确认的内容 | 未满足时的处理 |
|---|---|---|
| M0 启动 | 文档基线、Owner、首批场景、数据分类和评估计划 | 不进入 M1 设计 |
| M0 退出 | PoC、许可证、模型路由、关键开放问题和降级方案 | 延后或降级，不开始对应开发 |
| M1 设计 | API、DB、权限、UI 状态、测试和 Skills 证据 | 不进入实现 |
| M2 安全 | 租户隔离、ACL、缓存、对象、出域和审计 | 不进入客户试点 |
| M4 生产 | NFR、监控、备份、恢复、容量和回滚 | 不进入生产发布 |
| M5 上线 | 灰度、值守、回滚、恢复、培训和验收 | 不完成全量交付 |

评审结论必须写入项目决策记录或对应评审报告，并注明批准人、日期、遗留风险和截止版本。

## 9. 版本、链接与归档

- 文件名使用 `主题_v主版本.次版本_YYYY-MM-DD.md`
- 规范、契约和安全边界发生变化时至少递增次版本
- 兼容性破坏、范围变化或新的安全边界使用主版本升级
- 新版本批准后，旧版本标记为“已替代”，保留替代链接和失效原因
- 本地链接使用相对路径；外部来源记录仓库、路径、ref、commit SHA、许可证和核验日期
- `Skills/` 中的第三方内容只作为研发参考，不作为产品运行时依赖

## 10. 发布与交付归档

每次发布至少归档以下材料：

- 版本说明和变更影响矩阵
- API、数据库迁移和回滚说明
- 测试、RAG 评估、权限和安全报告
- 部署、备份、恢复、告警和灰度记录
- 已知问题、风险豁免和下一版本 Backlog
- 实际使用的 Skills、规则文件和验证证据
- 实际使用的 MCP、commit SHA、访问范围、产物和批准/例外证据

发布材料不得包含真实客户数据、生产口令、API Key、证书私钥、内部地址或未脱敏截图。

## V3 namespace and authority rules（追加，2026-08-09）

- Canonical task IDs 只有 `V3-T01`–`V3-T38`；heading、dependency、Backlog、evidence filename、commit example 和 matrix mapping 均使用这一 namespace。`V3-T01a`/`V3-T01b` 只能作为 V3-T01 内的串行 sub-slices，不是 Backlog task，不增加任务总数。
- FR acceptance IDs 为 `AC-V3-001`–`AC-V3-052`，NFR acceptance IDs 为 `AC-V3-NFR-001`–`AC-V3-NFR-018`。每个 FR/NFR 必须恰有一个 canonical AC、一个 primary task、API/DB/UI/security/test/evidence trace；完整细节由 v3 matrix authority 持有。
- v3 implementation order is `01_requirements.md` → `02_spec.md` → `03_plan.md` → `04_verification-matrix.md`; `03_plan_review.md` is the self-review and route-coverage companion. Baseline API/data/test/architecture docs retain history and only point to v3 authoritative sections.
- Sol final gate 已通过；v2 banner/status 现为 `已替代` 并带有 `superseded-by`，理由仅覆盖 frontend-only/no-backend/core-action-final-disabled boundaries；historical execution text remains intact。
- v3 task files, migration versions, API contracts and verification commands must be repo-relative or use the approved absolute venv paths; planned artifacts are not current evidence. No business code, tests, runtime config or Skills change is implied by document-only work.
