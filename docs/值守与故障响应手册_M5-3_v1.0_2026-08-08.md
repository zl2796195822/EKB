## 1. 值守职责

| 角色 | 职责 |
|------|------|
| 主值守 | 监控告警、初步诊断、执行 P0/P1 Runbook、更新事故记录 |
| 备值守 | 主值守无法响应时接手，协助处理复杂故障 |
| 技术负责人 | P0 故障升级联系人，负责架构级决策 |

值守班次：工作日 09:00–22:00（主值），其余时间待命（告警响应 ≤30 分钟）。

---

## 2. 告警分级与响应 SLA

| 级别 | 定义 | 响应时间 | 恢复目标 |
|------|------|----------|----------|
| P0 | 服务完全不可用；数据丢失风险；安全事件 | 5 分钟内 | 1 小时内 |
| P1 | 核心功能降级（QA 失败率 >10%，延迟持续超阈值）| 15 分钟内 | 4 小时内 |
| P2 | 次要功能异常，有降级方案 | 1 小时内 | 次日工作时间 |
| P3 | 轻微问题，不影响业务 | 次日工作时间 | 计划内处理 |

## 3. 常见故障 Runbook

### 3.1 API 服务不可用（/healthz 非 200）

**现象**：监控显示 healthcheck 失败，用户反馈登录/问答均报错。

**诊断**：
```bash
# 检查服务状态
curl -s http://127.0.0.1:8000/healthz
docker compose -f docker-compose.prod.yml ps api

# 查看最近日志
docker compose -f docker-compose.prod.yml logs api --tail=50
```

**处理**：
1. 若容器已退出，查看日志定位 panic/OOM 原因
2. 重启服务：`docker compose -f docker-compose.prod.yml restart api`
3. 确认 `/healthz` 恢复后通知用户
4. 若重启无效，执行 §4.1 API 回滚

**升级条件**：重启后 5 分钟内未恢复 → 升级 P0，通知技术负责人。

---

### 3.2 QA P95 延迟超阈值（>3s 持续 5 分钟）

**现象**：`/metrics` 端点 `qa_retrieval_duration_seconds` 或 `qa_generation_duration_seconds` 分位数偏高；用户反馈回答慢。

**诊断**：
```bash
# 查看指标快照
curl -s http://127.0.0.1:8000/metrics | grep qa_

# 查看 LLM 调用状态
curl -s http://127.0.0.1:8000/metrics | grep llm_calls

# 查看熔断器状态（日志中的 circuit_breaker 字段）
docker compose -f docker-compose.prod.yml logs api --tail=100 | grep circuit
```

**处理**：
1. 若 LLM provider 超时：检查外部 API 可用性，等待自然恢复或切换 provider（修改 `EKB_MODEL_PROVIDERS`）
2. 若检索慢：检查数据库连接数和慢查询日志
3. 若降级率升高（`qa_degradations_total` 增加）：属于可接受降级，记录并观察

**升级条件**：持续 15 分钟且无改善 → 升级 P1。

---

### 3.3 LLM 熔断器开闸（circuit breaker OPEN）

**现象**：日志出现 `circuit_breaker_state: OPEN`；问答走降级 demo 拼接，`qa_degradations_total{reason="llm_unavailable"}` 持续增加。

**诊断**：
```bash
docker compose -f docker-compose.prod.yml logs api --tail=50 | grep -i "circuit\|breaker\|llm"
curl -s http://127.0.0.1:8000/metrics | grep llm_calls
```

**处理**：
1. 确认外部 LLM API 是否可用（直接 curl 测试端点）
2. 熔断器会在 `EKB_CB_RECOVERY_TIMEOUT`（默认 60s）后自动进入 HALF_OPEN 探测
3. 若 LLM API 恢复，熔断器会自动关闸，无需手动干预
4. 若 LLM API 长时间不可用，考虑切换到备用 provider

**升级条件**：LLM API 宕机超过 30 分钟 → 升级 P1，通知用户服务降级。

---

### 3.4 数据库连接失败

**现象**：API 日志出现 `OperationalError` 或 `connection refused`；所有需要 DB 的端点返回 500。

**诊断**：
```bash
docker compose -f docker-compose.prod.yml ps postgres
docker compose -f docker-compose.prod.yml logs postgres --tail=30

# 测试连接（SQLite 模式）
ls -lh ekb_dev.db

# PostgreSQL 模式
docker compose -f docker-compose.prod.yml exec postgres pg_isready -U ekb -d ekb_prod
```

**处理**：
1. 若 PostgreSQL 容器退出：`docker compose -f docker-compose.prod.yml restart postgres`，等待 healthcheck 通过后重启 api
2. 若 SQLite 文件损坏：执行数据恢复（见 §4.3）
3. 确认数据库恢复后重启 API

**升级条件**：5 分钟内无法恢复 → 升级 P0。

---

### 3.5 问答降级率异常（>10%）

**现象**：`qa_degradations_total` 快速增长，用户收到 demo 拼接答案（无真实引用）。

**诊断**：
```bash
curl -s http://127.0.0.1:8000/metrics | grep degradation
docker compose -f docker-compose.prod.yml logs api --tail=100 | grep "llm_failed\|llm_unavailable"
```

**处理**：
1. 区分 `llm_unavailable`（LLM 未配置）vs `llm_failed`（调用失败）
2. `llm_unavailable`：检查 `EKB_MODEL_PROVIDERS` 配置是否正确
3. `llm_failed`：检查 API Key 是否有效、配额是否耗尽
4. 临时修复：更新 `.env`，重启 api 容器

---

### 3.6 越权拒绝数异常波动

**现象**：审计日志中 `action="kb:read"` 或 `action="qa:ask"` 的 `result="failure"` 记录激增；可能是扫描或配置错误。

**诊断**：
```bash
# 查询最近审计日志
curl -H "Authorization: Bearer $TOKEN" \
  "http://127.0.0.1:8000/api/v1/admin/audit?result=failure&page_size=20"
```

**处理**：
1. 检查 IP 来源：若集中在单 IP → 可能是扫描攻击，通过防火墙/WAF 封锁
2. 检查 actor_id：若是合法用户 → 可能是权限配置错误，检查 KbMembership
3. 触发安全告警，记录 trace_id，保留审计日志

**升级条件**：怀疑存在真实入侵 → 立即升级 P0，通知安全负责人。

---

### 3.7 磁盘空间告警

**现象**：`df -h` 显示磁盘使用率 >80%；可能影响备份、日志和数据库写入。

**处理**：
```bash
# 定位大文件
du -sh /var/lib/docker/volumes/* | sort -rh | head -10

# 清理旧日志（Docker 日志轮转已配置，但可手动触发）
docker system prune -f --volumes

# 清理旧备份（保留最近 7 份）
ls -t /app/backups/*.db | tail -n +8 | xargs rm -f
```

## 4. 回滚操作手册

### 4.1 API 服务回滚

```bash
# 1. 查看可用镜像版本
docker images ekb-api

# 2. 修改 docker-compose.prod.yml 中 image 字段为上一版本
# image: ekb-api:v1.0.1 → ekb-api:v1.0.0

# 3. 重新部署
docker compose -f docker-compose.prod.yml up -d api

# 4. 验证
curl -s http://127.0.0.1:8000/healthz
```

### 4.2 前端回滚

```bash
# 同上，修改 web 服务 image 版本后重部署
docker compose -f docker-compose.prod.yml up -d web
```

### 4.3 数据库恢复（SQLite）

```bash
# 列出可用备份
ls -lt /app/backups/

# 恢复指定备份（含完整性校验）
cd /Users/alin/EKB
.venv/bin/python scripts/restore.py --backup /app/backups/ekb_backup_20260808T120000Z.db

# 恢复后重启 API
docker compose -f docker-compose.prod.yml restart api

# 验证
curl -s http://127.0.0.1:8000/healthz
```
