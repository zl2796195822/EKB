## 1. 项目背景与目标

### 1.1 背景

企业制度、SOP、产品资料、运维手册、历史工单和客户配置通常分散在网盘、工单系统、Wiki 和本地文件中。用户面临信息入口分散、关键词检索命中率低、经验难沉淀等问题；直接使用通用大模型又存在无依据生成、引用不可核验和越权泄露风险。

EKB 采用“授权检索 → 证据编排 → 受控生成 → 引用与审计”的路线。产品目标不是替代源系统，而是在授权范围内提供统一入口和可追溯问答。

### 1.2 业务目标（指标为初始假设）

| 编号 | 目标 | 初始目标值 | 测量与冻结方式 |
|---|---|---:|---|
| G1 | 建立统一知识入口 | 首批接入 ≥5 类来源 | M0 盘点来源，M1 验收接入清单 |
| G2 | 提供可信问答 | 评估集首答准确率 ≥80%，M4 目标 ≥85% | 由 QA 建立脱敏评估集，采用人工标注规则 |
| G3 | 降低知识查询成本 | 试点用户自报查询耗时下降 ≥30% | 上线前后对同一任务做基线对比 |
| G4 | 保证数据边界 | 权限测试无跨租户可见数据；敏感数据按策略不出域 | 安全测试、审计抽样和模型路由记录 |
| G5 | 支撑客户知识服务 | 客户租户仅访问授权知识，满意度 ≥85% | 试点客户反馈；满意度问卷口径在 M0 冻结 |

> 原文中“行业普遍比例”“平均耗时”等数字缺少可核验来源，已改为待建立基线的项目指标，避免把未经验证的统计当作承诺。

### 1.3 指标口径

- **首答准确率**：评估集问题中，第一轮回答同时满足“结论正确、未越权、引用支持结论”的比例。
- **引用正确率**：展示的引用确实包含支持回答所需的原文，且文档版本、章节和定位可复核的比例。
- **拒答率**：被标注为证据不足的问题中，系统明确拒答且未生成无依据结论的比例。
- **问答延迟**：从服务端收到请求到首个有效事件、以及到完整回答结束分别记录；P95 必须注明采用哪一个口径。
- **满意度**：由试点用户按固定问卷和样本范围反馈，不能直接用点赞数替代。

### 1.4 非目标（v1.0）

- 不做开放域闲聊；无证据时必须明确说明无法确认。
- 不做模型训练或微调；仅保留后续评估和适配接口。
- 不做图像/视频生成；文档中的图片、表格和 OCR 解析属于入库范围。
- 不替代工单、CRM 或源系统；v1.0 只读同步，写回和深度编排另行立项。
- 不在 MVP 同时引入所有可选基础设施；先以最小可运行链路验证容量和质量。

## 2. 用户与场景

### 2.1 目标用户

| 角色 | 主要诉求 | 关键权限 |
|---|---|---|
| 内部运维工程师 | 快速查找故障案例、SOP 和部署手册，答案可复核 | 问答、检索、反馈 |
| 知识管理员 | 管理文档、权限、版本和知识覆盖度 | 上传、编辑、发布、治理 |
| 新员工 | 通过多轮问答学习业务流程和历史经验 | 授权范围内只读 |
| 外部运维客户 | 仅访问自身租户被授权的知识 | 租户内只读/问答 |
| 平台管理员 | 管理租户、模型策略、审计、配额和运行状态 | 平台级管理，跨租户操作必须审计 |

### 2.2 关键使用场景

- **US-01 内部问答**：用户询问故障排查步骤，系统返回结论、证据片段、文档章节和更新时间。
- **US-02 案例沉淀**：知识管理员导入历史工单或复盘资料，完成清洗、标签、权限设置和发布。
- **US-03 新人学习**：用户在同一会话中连续追问，系统保留必要上下文且不突破原有权限。
- **US-04 客户服务**：客户登录专属租户，只能检索本租户和被授权知识；跨租户请求默认拒绝。
- **US-05 治理审计**：管理员查看低置信度问答、越权尝试、知识覆盖盲区和模型降级事件。

## 3. 开源方案初筛与选型

> 本章是技术初筛，不是许可证法律意见。正式采用前必须固定依赖版本、保存许可证文本、核验分发义务和商用限制。

### 3.1 方案比较

| 方案 | 定位 | 优点 | 风险/限制 | 当前结论 |
|---|---|---|---|---|
| RAGFlow | 文档理解与 RAG 引擎 | 复杂文档解析能力较完整，适合作为引擎适配对象 | 版本升级、内部数据模型和部署依赖需验证 | **M0 首选候选** |
| Dify | LLM 应用编排与知识库 | 工作流和 Agent 编排较快 | 多租户交付和品牌/许可条款需逐版本核验 | 备选，不作为默认底座 |
| FastGPT / AnythingLLM | 开箱即用知识问答 | 上手快，适合轻量验证 | 多租户、扩展性和许可边界需核验 | 仅作对比或 PoC 备选 |
| LangChain / LlamaIndex | 编排框架/库 | 灵活、可自建 | 切分、评估、权限和运维成本由项目承担 | 作为适配层组件，不直接等于产品方案 |

### 3.2 选型原则

1. 权限过滤必须发生在检索和上下文构建之前，不能只依赖前端隐藏。
2. 业务数据模型、租户模型和审计模型与 RAG 引擎解耦，保留替换能力。
3. MVP 先采用最少基础设施，只有容量、检索能力或可观测性不足时再扩容或拆分。
4. 外部模型调用必须可按租户、数据分类和故障策略关闭，并记录路由与降级事件。

### 3.3 当前推荐

MVP 采用“FastAPI 业务单体 + RAGFlow 适配层 + PostgreSQL/pgvector + Redis + 对象存储”。RAGFlow 负责解析、索引和检索能力，业务层负责认证、租户、权限、会话、审计、配额和 API 契约；二者通过内部 API 和服务身份认证通信。

## 4. 系统架构设计

### 4.1 分层架构

```text
Web 门户 / 管理后台 / 客户门户 / OpenAPI
              │ HTTPS；问答接口返回 text/event-stream
        网关：TLS、路由、限流、SSE 透传
              │
业务应用（FastAPI 模块化单体）
  ├─ 身份、租户、RBAC/ACL、会话、配额、审计
  ├─ 知识库/文档 CRUD 与入库任务编排
  ├─ 检索授权与上下文策略
  └─ RAG Adapter（固定内部契约，屏蔽引擎差异）
              │
RAG 引擎（M0 以 RAGFlow 为候选）
  ├─ 解析、清洗、切分、向量化
  ├─ 混合检索、RRF、Rerank
  └─ Prompt 编排与模型调用
              │
PostgreSQL/pgvector + Redis + S3 对象存储
（规模化时按指标引入 Elasticsearch、Milvus、队列或 K8s）
```

### 4.2 技术栈基线

| 层 | MVP 基线 | 触发升级的条件 |
|---|---|---|
| 前端 | React + TypeScript + Vite | 多端交付或 SSR 需求经评审后再调整 |
| API/业务 | Python FastAPI 模块化单体 | 团队边界、吞吐或发布独立性形成明确瓶颈 |
| 网关 | Nginx 或 APISIX | 需要更复杂的路由、策略或多集群治理时评估 |
| RAG | RAGFlow 适配层 | 质量、性能、许可证或可维护性不达标时替换 |
| 关系库/向量 | PostgreSQL + pgvector | 向量量级、写入吞吐或隔离要求超过基线时评估 Milvus |
| 全文检索 | PostgreSQL 全文能力或引擎自带索引 | 复杂 BM25、规模或运维需求明确时引入 Elasticsearch |
| 缓存/任务 | Redis；长任务由任务表或轻量队列承载 | 并发和可靠投递要求超出单体能力时拆分 |
| 对象存储 | S3 兼容对象存储 | 按许可证、备份、性能和私有化能力评审具体实现 |
| 模型 | 本地模型优先，外部 OpenAI 兼容 API 受策略控制 | 以评估集、延迟、成本和数据策略决定 |

### 4.3 关键架构约束

- 所有租户边界在 API、数据库查询、向量检索、对象存储和缓存层同时校验。
- RAG 引擎只接收业务层已经授权的检索范围，不自行推断用户权限。
- 密钥、令牌、证书和服务器信息通过环境变量、密钥管理服务或受控部署清单注入。
- 长任务必须有幂等键、重试上限、失败状态和可恢复记录。

## 5. 核心 RAG 流水线

### 5.1 文档入库

```text
上传/只读同步
  → 格式解析（PDF/Word/Excel/PPT/Markdown/TXT/图片 OCR/网页）
  → 清洗去噪（页眉页脚、水印、乱码、重复内容）
  → 结构化切分（标题、条款、段落、表格，保留章节路径）
  → 写入元数据（租户、知识库、来源、更新时间、可见范围、标签）
  → 向量化 + 关键词索引
  → 原文入对象存储，元数据和检索索引入数据层
```

切分参数（chunk 600–800 token、overlap 80–120）仅作为 PoC 起点，必须在评估集上调参。每个 chunk 至少包含 `tenant_id`、`kb_id`、`doc_id`、章节路径、更新时间、可见范围和权限标签。

### 5.2 在线问答

```text
用户请求
  → 身份校验、租户/知识库授权、配额检查
  → 本地规范化（去除明显的提示注入和非法控制字段）
  → 生成授权过滤条件
  → 可选 Query Rewrite（仅在数据策略允许时调用模型）
  → 混合检索（向量 + BM25）
  → RRF 融合 → Rerank → 上下文构建
  → 受控生成（仅依据授权上下文）
  → 系统侧拼装引用、置信度、审计和反馈入口
```

权限检查必须早于任何可能把问题发送给外部模型的步骤；查询改写不得绕过租户、知识库和文档级过滤。

### 5.3 可信度与防幻觉

- Prompt 分为角色约束、知识约束和输出约束；无足够证据时返回“根据现有知识库无法确认”。
- 引用由系统根据检索结果生成，模型只能选择授权的证据片段，不允许自由编造文档名或链接。
- 置信度阈值由评估集标定，不把单一相似度阈值（例如 0.3）写成跨模型通用常数。
- 低置信度回答进入审核队列；审核结果应能关联原问题、证据、模型版本和知识版本。

### 5.4 性能、缓存与一致性

- 允许缓存 query embedding 和公开、版本稳定的片段；问答结果缓存默认关闭或必须绑定 `tenant_id`、主体权限摘要、知识版本、模型/Prompt 版本和策略版本。
- 文档更新、权限变更、模型策略变更时，应使受影响缓存失效。
- SSE 接口使用 `POST /api/v1/qa/ask` 返回 `text/event-stream`；客户端需支持取消、超时、重连提示和降级状态。

## 6. 多租户、权限、认证与审计

### 6.1 多租户隔离

- 租户是默认隔离单元；所有业务表、检索元数据、对象存储路径和缓存键都带租户边界。
- MVP 使用共享库 + 强制 `tenant_id` 过滤；高敏租户可升级为独立 schema、数据库、collection 或存储桶。
- 平台管理员的跨租户操作必须显式授权、二次确认并写入审计；普通用户不存在跨租户查询路径。

### 6.2 权限模型

- 知识库可见性：`PRIVATE`（创建者和明确分享者）、`TEAM`（租户内指定团队/成员）、`PUBLIC`（租户内可读）。
- 知识库角色：`OWNER`、`ADMIN`、`EDITOR`、`VIEWER`；角色能力必须映射到明确的 API 操作。
- 检索前计算用户的有效授权范围，向量检索、全文检索和引用生成使用同一范围；前端隐藏不能代替后端拒绝。

### 6.3 认证与审计

- 认证支持短期 Access Token + 可撤销 Refresh Token；外部租户可按 OpenID Connect/OAuth2 需求接入。
- 密码、Token、API Key 和证书不得写入数据库明文或文档；模型配置保存 `secret_ref`，真实密钥由密钥管理服务提供。
- 审计至少覆盖登录、权限变更、文档操作、检索、问答、引用、越权拒绝、模型路由和降级。问题与回答按数据策略脱敏、加密、限权和设定留存期限。

## 7. 核心数据模型

| 实体 | 关键字段（示例） | 约束/说明 |
|---|---|---|
| User | `id, name, email, status` | 身份可跨租户复用，不直接把用户固定在单一租户 |
| TenantMembership | `user_id, tenant_id, tenant_role, status` | 用户与租户的关系；平台级角色单独建模 |
| PlatformMembership | `user_id, platform_role, status` | 平台管理员的跨租户能力，所有操作必须审计 |
| Team/Group | `id, tenant_id, name, status` | `TEAM` 可见性和批量授权的成员集合 |
| KnowledgeBase | `id, tenant_id, name, visibility, owner_id, version` | 文档集合与权限边界 |
| Membership/ACL | `user/group_id, kb_id, role, expires_at` | 知识库角色和显式授权 |
| Document | `id, tenant_id, kb_id, title, source, mime, status, version, checksum` | 支持幂等入库、软删除和版本追踪 |
| Chunk | `id, tenant_id, kb_id, doc_id, content, vector_ref, section_path, metadata` | 向量可在 pgvector 或外部向量库；必须带权限元数据 |
| Conversation | `id, tenant_id, user_id, title, policy_version` | 受租户和主体权限约束 |
| Message | `id, conversation_id, role, content, citations, confidence, model_version` | 敏感内容按策略脱敏和留存 |
| ModelConfig | `id, tenant_id?, type, provider, endpoint, secret_ref, policy` | 不保存明文 API Key；租户覆盖需有优先级规则 |
| AuditLog | `id, tenant_id, actor_id, action, target, result, trace_id, created_at` | 不可静默修改；访问本身也需审计 |

## 8. 功能需求（EARS 风格）

> 优先级：P0 必须、P1 重要、P2 可选。每条需求应在测试用例中绑定成功、失败和权限边界场景。

### 8.1 知识库与文档管理

- **FR-KB-01（Event，P0）**：当具备 `EDITOR` 及以上权限的用户上传受支持文档时，系统应异步完成解析、切分、索引，并将状态从 `PROCESSING` 更新为 `READY` 或 `FAILED`。
- **FR-KB-02（Ubiquitous，P0）**：系统应支持 PDF、Word、Excel、PPT、Markdown、TXT、图片 OCR 和网页 URL 作为首批入库来源；实际格式清单在 M0 固定。
- **FR-KB-03（Unwanted，P0）**：当解析失败或格式不受支持时，系统应保留失败状态、可读原因、trace_id 和重试入口，不得把半成品用于问答。
- **FR-KB-04（Event，P1）**：当管理员配置只读数据源同步任务时，系统应按计划增量拉取、幂等更新并记录源系统游标，不修改源系统。
- **FR-KB-05（State，P0）**：文档处于 `PROCESSING`、`FAILED`、`DELETED` 状态时，不得参与检索和引用。
- **FR-KB-06（Optional，P2）**：启用版本管理时，系统应保留历史版本、差异摘要和回滚记录。

### 8.2 AI 问答

- **FR-QA-01（Event，P0）**：用户提交问题后，系统应依次执行授权、检索、重排、生成，并通过 `text/event-stream` 返回可取消的流式结果。
- **FR-QA-02（Ubiquitous，P0）**：有依据的回答应附带系统生成的文档名、章节、版本和可跳转定位；无依据回答应明确标记。
- **FR-QA-03（Unwanted，P0）**：检索证据不足时，系统应拒绝编造，返回无法确认提示和建议查阅方向。
- **FR-QA-04（State，P0）**：同一会话内系统应保留必要的多轮上下文；每轮上下文都必须重新应用当前权限。
- **FR-QA-05（Ubiquitous，P0）**：检索、上下文构建和引用生成不得包含用户无权访问的内容。
- **FR-QA-06（Optional，P1）**：启用反馈时，系统应记录点赞/点踩、原因和关联证据，用于质量分析，不直接自动修改生产知识。
- **FR-QA-07（Unwanted，P1）**：LLM 超时或不可用时，系统应按租户策略切换备用模型或返回可解释的降级结果，并记录事件。

### 8.3 检索与全文搜索

- **FR-SE-01（Ubiquitous，P0）**：系统应提供向量检索、关键词检索、融合和精排能力，具体实现可由 RAG Adapter 替换。
- **FR-SE-02（Event，P1）**：用户按关键词、标签、时间或来源筛选时，系统应仅在其授权范围内执行结构化过滤。

### 8.4 多租户与权限

- **FR-AC-01（Ubiquitous，P0）**：系统应以 `tenant_id` 隔离业务、索引、对象和缓存数据；跨租户访问默认拒绝。
- **FR-AC-02（Ubiquitous，P0）**：系统应实施 RBAC + ACL，并支持知识库角色和显式授权过期。
- **FR-AC-03（Event，P0）**：权限或成员变更后，新的授权范围应立即生效，并使受影响的检索/问答缓存失效。
- **FR-AC-04（Unwanted，P0）**：检测到越权请求时，系统应拒绝、返回统一错误、记录告警并避免泄露资源是否存在。

### 8.5 管理、运营与审计

- **FR-OP-01（Ubiquitous，P0）**：系统应提供受权限控制的审计查询与导出能力，并按留存策略处理敏感字段。
- **FR-OP-02（Ubiquitous，P1）**：系统应提供问答量、准确率、引用正确率、拒答率、低置信度队列、知识覆盖和活跃度看板。
- **FR-OP-03（Event，P1）**：平台管理员配置模型时，系统应支持按全局/租户/场景设置路由、数据策略、超时和降级规则。
- **FR-OP-04（Ubiquitous，P2）**：系统应支持按租户设置问答、存储、并发和外部模型调用配额。

## 9. 接口设计概要

| 模块 | 方法与路径 | 说明 |
|---|---|---|
| 认证 | `POST /api/v1/auth/login`、`POST /api/v1/auth/refresh` | 返回短期访问凭证；错误信息不泄露账号存在性 |
| 知识库 | `GET/POST/PATCH/DELETE /api/v1/kb` | 所有写操作校验租户和知识库权限 |
| 文档 | `POST /api/v1/kb/{kb_id}/docs` | multipart 上传，返回任务 ID；支持幂等键 |
| 文档状态 | `GET /api/v1/kb/{kb_id}/docs/{doc_id}` | 返回状态、失败原因、版本和更新时间 |
| 问答 | `POST /api/v1/qa/ask` | `Accept: text/event-stream`；支持 request_id、取消和降级事件 |
| 会话 | `GET /api/v1/conversations`、`GET /api/v1/conversations/{id}/messages` | 仅返回当前主体可见会话 |
| 检索 | `POST /api/v1/search` | 返回授权片段和引用元数据，不返回隐藏字段 |
| 反馈 | `POST /api/v1/qa/messages/{id}/feedback` | 记录反馈与原因 |
| 管理 | `/api/v1/admin/tenants`、`/api/v1/admin/models`、`/api/v1/admin/audit` | 平台权限和二次确认 |

所有接口经网关鉴权、限流和 trace_id 传递；对外 OpenAPI 使用独立凭证、最小权限和版本化契约。

## 11. 私有化部署与密钥管理

### 11.1 部署分级

- **PoC/小规模**：Docker Compose，按 RAG 引擎实际依赖部署业务服务、RAG 服务、PostgreSQL、Redis 和对象存储。
- **生产强化**：按容量和可用性需求评估 K8s、独立向量库、消息队列、模型推理集群和多副本网关。
- **模型路由**：本地模型为默认优先级；外部 API 必须经过数据策略、租户策略、超时、预算和审计检查。

### 11.2 环境信息安全规范

真实服务器地址、域名、SSH 端口、账号、口令、证书和 API Key 不写入仓库文档。部署清单只保留占位符：

```bash
ssh -p "${EKB_SSH_PORT}" "${EKB_SSH_USER}@${EKB_DEPLOY_HOST}"
```

应用层配置使用环境变量、`.env`（必须加入 `.gitignore`）或密钥管理服务，例如 `${EKB_DB_PASSWORD}`、`${EKB_LLM_API_KEY}`。若历史文档、聊天记录或日志曾出现真实凭据，应立即轮换并检查访问记录。

## 13. 风险与对策

| 风险 | 影响 | 对策/触发动作 |
|---|---|---|
| 许可证或依赖版本变化 | 交付受限 | 固定版本、保存许可证、上线前复核并保留替换适配层 |
| 检索质量不足 | 答非所问、幻觉 | 建评估集，调切分/检索/Rerank，跟踪引用正确率和拒答率 |
| 权限或缓存越权 | 合规事故 | 检索期过滤、权限单测、跨租户测试、缓存键绑定主体策略 |
| 数据质量差 | 输出过期或重复 | 来源治理、checksum 去重、更新时间、版本和下线流程 |
| 提示注入或恶意文档 | 绕过指令或泄露上下文 | 文档内容与系统指令分离、输入/输出审查、红队测试 |
| 外部模型不稳定或数据出域 | 体验、成本和合规波动 | 数据策略、超时/熔断、备用模型、路由审计和租户配额 |
| 私有化算力不足 | 延迟高、无法并发 | M0 实测，量化/小模型/异步入库，按容量触发扩容 |
| 审计含敏感内容 | 二次泄露 | 脱敏、加密、最小权限、留存期限和导出审批 |
| 需求范围蔓延 | 延期 | MVP 非目标、变更评审、里程碑门禁和风险 Owner |
