# EKB 知识库批量目录上传修复与开源对标

## 结论

“知识库列表加载失败”不是列表请求失败：空数组被前端当成错误状态，导致没有可选上传目标。目录上传还把每个文件创建成独立 `FILE` 批次，丢失了目录作为一个可追踪批次的语义。

本次修复后，空列表会显示“创建并选择”知识库入口；用户创建后可立即把目录上传到该目标。在 `1000` 个文件和 `5 GB` 的服务端上限内，一次多文件或目录操作创建一个 `MULTI_FILE` 或 `DIRECTORY` 批次；超过上限时按边界拆为多个可恢复分区。每个分区保留完整相对路径、逐项预检结果、共享 batch ID、受限并发、取消未开始项目与硬刷新后的 Upload Center 恢复依据。

这修复了页面和上传编排问题，但不把生产上传/索引描述为已完成：生产仍需要 S3/MinIO 兼容对象存储、远程 embedding provider/profile 和可靠 ingest worker/scheduler 才能从对象上传到 `READY`。

## 已修复行为

| 旧行为 | 新行为 | 实现位置 |
|---|---|---|
| `knowledge.list()` 返回 `empty + []` 时显示“知识库列表加载失败” | 空列表是正常状态，显示私有知识库创建输入和“创建并选择”按钮 | `BatchUploadModal.tsx` |
| 没有目标知识库时无法继续上传 | 新建完成后选中该 KB，随后上传请求使用新 ID | `BatchUploadModal.tsx` |
| 每个目录文件独立创建 `FILE` batch | 单个合法分区共享一个 `DIRECTORY` 或 `MULTI_FILE` batch；超出 `1000` 文件或 `5 GB` 时自动拆分 | `documents.ts` |
| 同一操作的预检、失败、恢复记录分散 | 服务端预检逐项返回；拒绝项不传对象或可续传 ID；成功项保留原 batch/item ID | `documents.ts`、`BatchUploadModal.tsx` |
| 失败重传新建子集 batch，可能重复版本 | 重传原服务端 item；服务端已完成而响应丢失时返回 `already_completed`，不重复 complete | `documents.ts`、`storage.py` |
| 所有 session 在排队前创建，后段 URL 会过期 | create 只预检；worker 真正开始 PUT 前打开并续租 session | `documents.ts`、`storage.py` |
| 相同清单永久命中旧幂等记录 | 幂等 key 绑定一次上传 operation；同一网络重试复用，重新选择目录会生成新 operation | `documents.ts`、`BatchUploadModal.tsx` |

上传协议为：创建 batch 并逐项预检 → worker 在实际传输前打开/续租单项 session → 浏览器受限并发 PUT 对象 → SHA-256 complete → 异步 ingest。客户端取消只终止尚未开始的项目，已经开始的对象传输保持由服务器状态机和 Upload Center 投影管理。`REJECTED`、完成态或缺失完成投影的上传项无法通过 session/abort 接口绕过状态机。

四个项目的共同成熟做法是：上传不是页面内的多个孤立请求，而是可恢复的服务器资源；每个文件有独立状态，但目录有统一 batch、来源路径、失败原因和后台任务投影。EKB 现在已对齐这条最小上传协议，尚未对齐解析质量、对象存储、连接器增量同步、向量索引和生产可观测性。

## 不能直接移植的原因

不建议把任何一个候选项目整体并入 EKB。它们的身份模型、存储、任务队列、数据库和许可边界与 EKB 的多租户、ACL、审计和既有 API 不同。直接复制会破坏授权预过滤、引用可追溯和已应用迁移不可变约束。

允许的复用顺序是：固定 commit → 文件级许可证/NOTICE/SBOM 审核 → 隔离 adapter 或独立服务 PoC → 租户/ACL/引用/失败回归 → 才考虑窄范围代码移植。禁止追踪上游 `main`、复制 Dify/Onyx `ee`/其他受限许可目录，或用外部系统绕过 EKB 的授权决策。
