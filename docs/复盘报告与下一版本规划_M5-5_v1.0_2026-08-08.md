## 4. 项目复盘

### 4.1 进展顺利的方面

**RAG 质量快速达标**：M1 阶段首答准确率即达 99%，远超 ≥80% 门槛。评估集、评估脚本、自动比较工具（`eval/run.py`、`eval/compare.py`、`eval/ab_compare.py`）在 M1 建立闭环，使 M4 优化有客观数据支撑。

**安全与权限内嵌入研发主线**：RBAC/ACL、越权拦截、租户路由/出域策略和配额从 M2 起全面落地，安全回归 16 项在 M4-7 交付，未将安全集中到上线前补做。

**性能优化效果显著**：M4-3 检索并行化 + 真流式 LLM，QA P95 从 4252ms 降至 2357ms（-45%），压测 QA P95 2715ms 达标；吞吐 +173%。两个原 FAIL NFR 指标均转 PASS。

**故障韧性完整**：熔断器（CLOSED/OPEN/HALF-OPEN）、embedding 降级（本地 n-gram）、LLM 降级（demo 拼接）、搜索超时 504、QA 超时 finish_reason 事件、权限变更缓存失效全部有故障注入测试覆盖，不是靠"代码注释"保证的。

**测试用例持续增长**：从 M1 的 65 passed 增长到 M4-7 后的 145 passed，关键路径（认证、租户隔离、熔断、安全回归、备份恢复）均有回归用例。

**文档体系完整**：Spec、API 契约、数据模型、部署手册、安全合规、测试策略、研发任务记录和评估报告共约 20 份文档随里程碑同步更新，决策记录可追溯。

### 4.2 遇到的挑战

**SQLite 横向扩展瓶颈**：M1 tracer-bullet 选择 SQLite 以降低早期依赖，带来的代价是 QPS 4.5 远低于 ≥50 目标，PostgreSQL 切换成为 v1.1 P0 优先级。当时决策合理（MVP 验证优先），但应在 M3 启动切换准备，而非推迟到 M5 后。

**流式 LLM 随机性拒答（G042/G077）**：`asyncio.to_thread(next, gen)` 的 `StopIteration` 问题在 M4-3 已修复（改用哨兵值），但 HTTP SSE 场景下偶发拒答根因仍未完全定位。本地直调正确、HTTP 调用偶发拒答的 diff 缩小工作未完成，成为遗留 P1 风险。

**M0 开放问题未形成人工决策**：OQ-001 至 OQ-009 的"首批场景/数据源/安全评审/私有化硬件"等问题在文档中标注了 Owner 和截止阶段，但实际执行中未有评审会记录和签字，导致 ADR-001/002/003/004 仍处于"提议"状态。这是流程执行层面的缺口，而非技术缺口。

**E2E 浏览器验收未完成**：Playwright 浏览器验收（M1 任务证据）标注"待启动服务后执行"，整个 v1.0 周期内未有截图存档和 E2E 用例文件，视觉回归和关键流程端到端链路缺少证据。

**安全评审签字缺失**：M2 退出准则中"安全负责人签署 M2 评审结论"未执行，M5 上线前须补；若实际团队小或安全合规角色兼任，应明确代理人和豁免记录。

### 4.3 过程改进建议

1. **PostgreSQL 迁移应在 M3 启动准备**：数据层切换影响范围大（ORM 驱动、迁移脚本、备份恢复、压测基线），不应留到生产前。建议在 M3 完成后立即开始数据层迁移分支，与 M4 生产强化并行。

2. **开放问题必须有"关闭证据"而非仅有 Owner 字段**：OQ-001 至 OQ-009 应要求在截止里程碑评审会上产出签字记录或明确降级决策，文档工具不能替代人工判断。

3. **E2E 测试应在 M1 阶段就自动化**：关键流程（登录 → 上传 → 问答 → 引用展示）的 Playwright 用例应随功能一起交付，而非推迟到"待启动服务后"。

4. **评估集 A/B 对比 fixture 应与功能同步交付**：Permission/Freshness/Adversarial 集扩充后，相应 fixture（角色 token、文档版本）应同步就绪，否则对比工具形同虚设。

5. **流式路径需要独立压力测试用例**：`asyncio.to_thread(next, gen)` 这类异步/同步边界问题只在生产 HTTP 场景下触发，单元测试和本地直调均无法覆盖；应在压测脚本中专门验证流式路径的随机性（多次同 prompt 跑，统计拒答率）。
