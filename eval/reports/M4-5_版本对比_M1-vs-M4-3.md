### 2.2 新失败题（2 题：G042、G077）

| ID | 问题 | baseline | candidate | finish_reason | 根因初步判断 |
|---|---|---|---|---|---|
| G042 | Redis used_memory_rss 指标反映什么？ | ✅ 正确 + 引用正确 | ❌ answer="证据不足，无法确认" | refusal | **流式 LLM 随机性拒答**：本地直接调 `generate_answer_stream(q, evidence)` 正确输出完整答案（`根据证据2...实际占用物理内存大小`），但评估中同一 prompt 回复"证据不足"。原因：流式解码 token 采样随机性（temperature 相同但 stream=true 时服务端采样序列可能不同），+ 2 题证据文本中关键词被排在 evidence[1] 第 2 位时流式更易触发拒答 |
| G077 | 回滚执行步骤的顺序是什么？ | ✅ 正确 + 引用正确 | ❌ answer="证据不足，无法确认" | refusal | 同 G042：流式 LLM 随机性拒答。evidence[0] 为"数据库故障 SOP"（连接池内容），evidence[1] 才是"部署回滚 SOP"，流式输出可能过早触发"证据不足"自识别逻辑 |

> **关键验证**：对 G042 单独复现——
> - `retrieve()` 返回 chunks 含"Redis 内存溢出 SOP / 内存诊断"（score=0.064，包含 `used_memory_rss` 关键词）
> - `build_context(chunks)` 产出 evidence[1] 含完整术语
> - `generate_answer(q, evidence)` 非流式 → **正确回答**
> - `generate_answer_stream(q, evidence)` 流式 → **正确回答**（本地脚本直调）
> - HTTP `/qa/ask` SSE → **拒答**（评估脚本场景）
>
> 结论：流式 HTTP 调用与 generate_answer_stream 本地直调不一致，疑似异步 SSE 事件消费速度差异 + LLM 流式 token 序列偶发。**非 M4-3 检索/上下文代码逻辑回归**。

## 5. 后续行动建议

1. **P1：流式拒答偶发根因定位**——G042/G077 本地直调正确但 HTTP SSE 拒答：缩小 diff（`qa.py` `event_stream()` 流式消费与本地直调的 prompt 构建/上下文传递差异），必要时加详细日志。
2. **P2：增加流式→非流式降级兜底**——当流式生成答案含 `"证据不足"` 且 `retrieve()` 返回 ≥3 chunks 时，提示词加一句"请再次核对证据 [1]~[n] 中是否存在答案关键词"做二次确认（避免流式 LLM 过早拒答）。
3. **P2：跑 Permission/Freshness/Adversarial 集对比**——M4-5 三集合已扩充但尚未做 A/B 对比（当前仅 golden/no-answer）。
4. **P3：compare.py 延迟类指标支持**——延迟 ms 属数值型，`_delta()` 跳过导致 `incomparable`；改为"降幅%"支持并纳入阈值回归。
